## Startup troubleshooting

Hostinger must execute `src/server.js` (`package.json` main and npm start), which calls listen without awaiting a database operation. If a startup selector is present, use that file; `src/app.js` exports the application factory and `public/index.html` is the frontend. Respect the provider-assigned PORT. Uploaded hosting logs enforced a three-second listen deadline; the regression test covers an unresponsive database without reporting it healthy.

After redeployment, check `/api.php?route=health`. A JSON 503 with `Database readiness check failed.` means HTTP is running but MySQL is unavailable; runtime logs record the error code without credentials. ETIMEDOUT/ECONNREFUSED/ENOTFOUND require checking the database hostname and access from the actual Node runtime with Hostinger. ER_ACCESS_DENIED_ERROR means credentials or account privileges need correction. ER_BAD_DB_ERROR means the database name is unavailable to this connection. ER_NO_SUCH_TABLE requires running the preserved, additive migration with the correct private environment. `Store provisioning is required.` means settings are missing, and new-store private provisioning is needed; do not seed an existing PHP database. A full hosting HTML 503 still indicates the runtime/listener is not available—check the selected entrypoint and current deployment logs.

Runtime startup diagnostics report entry/dependency/application phases and required variable names with set/missing status only. The direct entrypoint loads an ignored root .env file when present, preserving injected hosting variables. A `startup settings validation failed` message names the fixed validation requirement without revealing supplied values. An absent `src/server.js entry reached` marker in the latest deployed logs requires checking the selected entry file, commit and module-loading errors with hosting; do not change database passwords solely from a generic hosting HTML 503.

Keep the server entrypoint and its entire static import graph free of top-level await: Node.js require() rejects asynchronous ESM graphs with ERR_REQUIRE_ASYNC_MODULE before executing startup diagnostics. CLI workers must put await inside async functions and run only when their exact file path is the CLI entry. The startup suite exercises both normal Node invocation and a require()/listener-capture hosting model; the provider’s internal loader contract still requires account-level confirmation.
