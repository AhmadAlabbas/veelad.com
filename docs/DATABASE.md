# MySQL migration, import and rollback

No SQL export was provided. `data/seed.json` contains sample catalog data only. The two supplied artwork files are retained outside the checkout under `/workspace/migration-reference/veelad/veelad-app/uploads`; **do not publish or assign them to invented accounts**. They require original `uploads` table records and matching product ownership. Copy them to the private deployment upload path only as part of a verified import.

## Schema

`migrations/001-schema.json` preserves the PHP table columns and positional record layout: users, artists, products, orders, settings, messages, rate_limits, uploads, customer_state, password_resets, mail_queue and audit_log. Products/settings/order detail fields remain JSON in TEXT columns for compatibility. Currency is integer SAR halalas, not floating point. Adds a private MySQL sessions table and a checksum-based schema_migrations table. New sessions are isolated by database/environment and cookies remain host-only.

`npm run migrate` runs under a MySQL advisory lock and creates missing tables only; it does not seed, overwrite or drop records. Applied migration checksum mismatches fail. MySQL DDL auto-commits: repeatable `CREATE TABLE IF NOT EXISTS` allows an interrupted initial migration to resume; this is not a claim of transactional DDL. Transaction-sensitive existing tables must use InnoDB; the migrator rejects imported engines that break this requirement. Back up before schema changes. Never edit an applied migration; add reviewed additive migrations. This initial compatibility migration deliberately avoids deleting or restructuring the PHP schema.

For `APP_ENV=staging`, the server invokes this same migrator automatically after registering the HTTP listener, using the hosting runtime's environment variables. It does not require Node.js in the account's SSH shell or build-time database credentials. APIs remain unavailable until the migration completes successfully; failures do not report a healthy store. Existing settings, users, catalog and orders are preserved, and no demo seed or administrator is created. Repeated deployments skip migrations with matching recorded checksums. Local and production startup do not migrate automatically; use the documented local setup and deliberate production migration steps. Staging backups are still required before deploying schema changes.

## Import a future export

1. Privately back up the original PHP database and artwork directory together while writes are paused. Request the complete schema/data export through secure storage, not a GitHub commit. Preserve IDs, JSON, password hashes, order request keys and guest hashes exactly.
2. Restore into an isolated **staging** MySQL database first using the official MySQL client. Use a permission-restricted temporary option file or password prompt; never place a password on the command line. Review any supplied SQL before execution and never direct an unreviewed export at production. A real database import is not performed because no export was supplied.
3. Run `npm run migrate` against that staging database. Compare counts of users/artists/products/orders/uploads before and after. Review exported schema compatibility, JSON validity, unique constraints and InnoDB engines. Run `node --env-file-if-exists=.env scripts/audit-import.js`; it reports password algorithm and upload integrity counts without exporting user data or hashes. Copy verified files with the original paths to the private upload root. Fix missing ownership/associations from authentic records, never guesses.
4. PHP's default `password_hash` commonly uses `$2y$` bcrypt; Node verifies `$2a$`, `$2b$`, `$2y$`, `$argon2i$` and `$argon2id$`. Successful bcrypt/Argon2i logins are rehashed to Argon2id. Unsupported hashes require an explicit recovery strategy and enabled/tested email, not silent account replacement. Actual hash algorithms remain unknown until the database is supplied. Password changes/reset invalidate all sessions through password stamps; PHP sessions require re-login.
5. Disable PHP writes before the final cutover export, repeat the verified import and counts, then route the deployment to Node. Do not run PHP and Node against the same writable production database during migration. Imported queued mail may contain old reset links: reconcile or quarantine those messages before enabling the new worker. Do not automatically resend historical paid-order emails.
6. Keep staging and production entirely separate. Remove real customer information from staging if a production export is used there; run staging tests using fictional accounts and mapped artwork fixtures. Validate original-order private guest tokens in the restored data and confirm no uploads are publicly reachable except approved products.

## Backups and rollback

Store encrypted backups of each database and matching private artwork separately from GitHub/deployment artifacts. Test a restore into a temporary isolated database and validate counts/associations; a dump existing is insufficient proof of recovery. Record the deployed Git SHA, migration list/checksums, backup timestamp and upload snapshot for every release.

For this additive migration, preferred application rollback is a **revert commit**, tested through `main` → staging, then deliberately released to production. This keeps release branches linear and avoids force pushes or rewriting deployment history. If Hostinger provides a verified previous-build rollback, use it only after confirming the old code is compatible with the current schema and durable uploads; availability of this hosting feature is not established here. Revert to the retained PHP deployment only using its own restored database, configuration and private upload snapshot; Node and PHP must not write to a shared database during rollback.

If an incompatible data/schema change occurs, pause checkout/writes and worker, take a fresh recovery backup, restore the verified prior database AND artwork snapshot to a separate database/path, update that environment's private bindings, and switch to the matching reviewed application version. Never restore blindly over current paid orders: reconcile all orders/payments/refund work created after the backup with an operator. No destructive automatic down-migration is supplied.

Cancellation locks orders, restocks once and marks recorded paid orders `refund_required`; this does not execute a refund. The preserved 20% demo royalty field is a compatibility placeholder, not an agreed artist contract, ledger or payout instruction. No transfers occur.

Migration `006-google-auth.json` adds binary provider-subject identity mapping with one Google identity per user, plus session-bound expiring OAuth attempts. Include identities with users in backups; temporary OAuth states are deliberately excluded. No existing users or passwords are rewritten. See [Google sign-in](GOOGLE-SIGN-IN.md).

Migration 007 adds verified account email records (`account_emails`) and single-use expiring confirmation token hashes (`email_verification_tokens`). No `users` columns are changed. Verified addresses are backed up; temporary tokens are excluded. Retain additive tables on application rollback, disable email and verification enforcement first, and request fresh links after restore.
